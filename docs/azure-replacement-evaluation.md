# Import Pipeline Analyzer — Azure Replacement Evaluation

**Prepared for:** Engineering Leadership  
**Date:** May 22, 2026  
**Subject:** Custom TypeScript Import Analyzer vs. Azure-native Alternatives

---

## Background

The custom tool performs a multi-stage analysis of the "Generic Update" import pipeline. Its core technical challenge is that the three pipeline stages (Mapping, Validation, Submission) run on different Kubernetes pods with different `operation_Id` values in Application Insights. The submission job starts 0–15 minutes after the trigger on a completely new pod with no shared trace context. The tool resolves this via a "hop chain": anchor query → extract timestamps/pods → time-window search for the submission job. It then parses 26+ distinct log message patterns via regex, aggregates per-row timing, projects bottlenecks, and supports side-by-side import comparison.

## 4. Risk Assessment

### What breaks if you switch?

**Scenario 1 — Submission logs not found (affects ~100% of imports)**

The submission Kubernetes job starts on a new pod with no shared `operation_Id`. The custom tool finds it by searching for `ImportGenericUpdateApprovedContent: MappedContentCount` in a 15-minute window after `SaveApprovedRecords`. Neither alternative can execute this conditional time-window search. Result: submission timing data is unavailable for every import analyzed.

**Scenario 2 — Validation fallback fails silently**

When `operation_Id` is not present in the anchor logs, the tool falls back to pod name + time window to find the validation `operation_Id`. This fallback is a second KQL query conditioned on the first result. Neither alternative supports this. Result: validation data is missing for imports where the anchor query returns no `operation_Id`.

**Scenario 3 — Comparison regression analysis**

The team uses two-import comparison to identify regressions between releases. Workbooks cannot do this. Azure OpenAI can attempt it but the structured diff (sorted by `|deltaMs|`, flagged by percentage change) will be inconsistently formatted. Result: regression analysis workflow is broken or manual.

**Scenario 4 — New log pattern added to the pipeline**

The pipeline team adds a new checkpoint step. In the custom tool, this is a one-line addition to `logCatalog.ts`. In Workbooks, a KQL tile must be updated. In Azure OpenAI, the prompt may or may not pick it up depending on whether the new log message matches the existing extraction regex.

### Impact on non-technical users

The custom tool accepts a UUID and a natural language question and returns a structured, human-readable analysis with flagged bottlenecks and projected timings. Non-technical users (support, operations) can use it without understanding KQL or the pipeline architecture.

- **Alt A** preserves the natural language interface but introduces non-determinism. Users may get different answers to the same question on different days.
- **Alt B** requires users to know the UUID, understand what the tables mean, and interpret raw millisecond values without context. This is a significant regression for non-technical users.

### Maintenance burden

| Option | Burden | Notes |
|---|---|---|
| Custom tool | Medium | TypeScript codebase, test suite, deployment. Adding log patterns requires code changes and tests. |
| Alt A (Azure OpenAI) | Low–Medium | Prompt engineering is the primary maintenance surface. Log format changes require prompt updates. No deployment pipeline, but prompt drift is hard to detect. |
| Alt B (Workbooks) | Low | KQL-only. No deployment. But adding features requires KQL expertise and manual Workbook editing. |

## 6. Recommendation

### Recommended approach: Hybrid — Workbooks for monitoring + Custom Tool for investigation

Neither alternative can replace the custom tool for its primary use case: diagnosing a specific import's performance. The cross-pod correlation problem is architectural, not a tooling gap. The submission job's lack of a shared `operation_Id` means any tool that cannot execute conditional, multi-step queries will return incomplete data. This rules out both alternatives as full replacements.

### Action plan

**1. Keep the custom tool for investigation.**

It is the only option that reliably finds submission logs, handles the hop chain fallback, and produces the comparison diff. The codebase is well-structured (`logCatalog.ts` as a single source of truth, typed interfaces throughout) and maintainable.

**2. Build a Workbook for trending and monitoring.**

Workbooks are well-suited for aggregate views: how many imports ran this week, what was the average validation duration, which clients have the slowest imports. These queries are static, parameterized by date range, and do not require the hop chain. This gives operations teams a dashboard without requiring the custom tool for every question.

**3. Evaluate Azure OpenAI as an enhancement, not a replacement.**

If the team wants to add natural language querying on top of the custom tool's structured output, the right architecture is:

```
Custom tool resolves hop chain + fetches raw data
    → Azure OpenAI interprets the structured ImportAnalysis JSON
    → Generates a narrative explanation
```

This is strictly better than "on your data" because the LLM receives clean, structured data rather than raw log text. This path is already partially implemented in the `src/ai/` directory.

**4. Do not use "on your data" pointed directly at Log Analytics for this use case.**

The feature is designed for document search and Q&A, not for multi-step conditional log correlation. It will produce confident-sounding but incomplete answers whenever the submission hop chain is needed — which is every import.

### When to reconsider a full Azure OpenAI replacement

If the team decides to invest in a proper agentic loop (Semantic Kernel or LangChain with tool-calling), the hop chain logic could be expressed as a sequence of tool calls that GPT-4 orchestrates. This would be a significant engineering investment (~4–8 weeks) and would essentially rebuild the custom tool's orchestration layer in a different framework. It is worth considering for a v2 if the team wants to move away from maintaining TypeScript, but it is not a drop-in replacement today.
